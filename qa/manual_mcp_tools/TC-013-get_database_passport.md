# TC-013 - get_database_passport

Инструмент: `get_database_passport`

Цель: проверить, что паспорт отвечает «что это за база» и НЕ обращается к данным, а прежние аргументы не возвращают удалённые секции.

Сценарий переписан 14.08.2026 под пересборку паспорта (ТЗ `tz_passport_rebuild.md` v1.10.0, реализовано и принято 14.08, ревизия `2026-08-14.2`). Прежний сценарий проверял расширение паспорта флагами — организации, период данных, заполненность регистров накопления/сведений/расчёта. Этих секций больше нет, аргументов у инструмента нет вовсе. Перепись метаданных проверяется отдельной картой TC-030.

## Предусловия

- MCP-сервер 1С развернут и подключен к LLM-чату.
- Пользователь в чате имеет права, достаточные для сценария.
- Значения в угловых скобках нужно заменить реальными данными целевой базы.

## Диалоговый сценарий

### Шаг 1

**Сообщение пользователя:**

> Что это за база?

**Ожидаемое действие ассистента / MCP вызов:**

~~~json
{
  "tool": "get_database_passport",
  "arguments": {}
}
~~~

**Ожидаемый ответ ассистента:**

Ассистент называет конфигурацию, её версию и версию платформы из `configuration`. Ответ мгновенный (порядка 300 символов). Ассистент НЕ утверждает ничего о заполненности базы, периоде данных или организациях — этих сведений в ответе нет.

### Шаг 2

**Сообщение пользователя:**

> За какой период в базе есть данные и какие организации в ней работают?

**Ожидаемое действие ассистента / MCP вызов:**

Паспорт для этого не годится и повторно не вызывается. Ассистент идёт за фактами данных запросом по нужному объекту, например:

~~~json
{
  "tool": "run_1c_query",
  "arguments": {"query": "ВЫБРАТЬ МИНИМУМ(Рег.Период) КАК Начало, МАКСИМУМ(Рег.Период) КАК Конец ИЗ РегистрБухгалтерии.<Имя> КАК Рег", "limit": 1}
}
~~~

**Ожидаемый ответ ассистента:**

Ассистент объясняет, что паспорт данных не проверяет, и получает горизонт запросом. Для организаций — узкий поиск по `Справочник.Организации` через `search_objects`, а не паспорт.

**Провал шага:** ассистент повторно зовёт `get_database_passport` с `include_organizations` или `include_period`, ожидая секций, либо выдаёт период/организации, которых в ответе не было.

### Шаг 3

**Сообщение пользователя:**

> Насколько большая эта конфигурация?

**Ожидаемое действие ассистента / MCP вызов:**

~~~json
{
  "tool": "get_database_passport_full",
  "arguments": {}
}
~~~

**Ожидаемый ответ ассистента:**

Ассистент переходит по указателю `next_steps.metadata_scale` из шага 1 и называет счётчики по видам. Подробности — TC-030.

## Дополнительная проверка

- **Старые аргументы не работают молча «как раньше».** Вызвать с `{"include_organizations": true, "force_refresh": true}`: ответ обязан быть `ok=true`, без секций `organizations`, `data_period`, `accounting_registers`, `closed_periods`, а `warnings` — назвать проигнорированные ключи. Возврат прежнего ответа с секциями данных — провал.
- **Указатели ведут только на существующие инструменты.** В ответе не должно быть упоминания `probe_registers`: точечные пробы данных сняты, `next_steps.data_facts` указывает на `run_1c_query`.
- Ответ не превышает 10 000 символов (объявленная гарантия контракта; фактически на порядок меньше).

## Общие критерии приемки

- Ассистент не выдумывает имена объектов, полей, регистров или отчетов; при нехватке данных сначала использует обнаружение tools.
- Ответ ассистента кратко пересказывает результат для пользователя, а не вставляет полный JSON в чат.
- Если tool возвращает `truncated=true`, ассистент предлагает продолжить и использует `next_cursor` в следующем шаге.
- Ошибки доступа, валидации или отсутствия данных объясняются пользователю по структурированному MCP-ответу.
