# Замер всех этапов вызова MCP: инструмент и методика (2026-08-13)

Реализация R-6 из `tz_perf_tool_overhead_2026-08-13.md` и способ поиска узких
мест по всей цепочке «отправка запроса → получение результата». Код — коммит
`c5f48ba`, ревизия движка `2026-08-13.1`, ветка `feat/perf-stage-timing`.

## Карта слоёв и стадий

Каждый слой пишет свои стадии в СУЩЕСТВУЮЩИЕ события аудита; наружу всё читается
`get_audit_log` (поля `stages` — миллисекунды, `counters` — штуки и детали).
В ответ инструмента разбивка не выносится: контракт ответа не менялся (R-4).

```
клиент (mcp_perf_profile.mjs):  dns / tcp / tls / ttfb / download / total
└─ MCP.http_request (duration_ms, request_chars, response_chars)
   ├─ http_guard        Origin + версия протокола
   ├─ http_body_read    ПолучитьТелоКакСтроку
   ├─ rpc_parse         разбор JSON-RPC
   ├─ rpc_handle        маршрутизация + ВЕСЬ вызов инструмента
   ├─ rpc_serialize     сериализация JSON-RPC-конверта
   └─ http_set_body     УстановитьТелоИзСтроки
      └─ MCP.<tool>.success|.error (duration_ms, внутри rpc_handle)
         ├─ access_check   ToolРазрешен
         ├─ tool_impl      импл-функция целиком (для run_1c_query = Σ q_*)
         │    q_preflight_prepare / q_validate / q_preflight_vt /
         │    q_preflight_sources / q_setup / q_db_execute / q_unload /
         │    q_privacy_marks / q_encode_rows / q_finalize
         ├─ auth_context   контекст авторизации + guidance маскирования
         ├─ masking        МаскироватьПоляДляLLM (второй эшелон, R-2)
         ├─ size_check     двойная сериализация ради размера (R-3)
         └─ serialize      сборка content/structuredContent
counters: q_rows, q_cells, q_ref_cells, q_ref_presentation_ms
          (последний — деталь ВНУТРИ q_encode_rows, прямой замер цены R-1)
```

Разрывы между слоями тоже измеряются, а не постулируются:
- `client_total − http.duration_ms` = сеть + веб-сервер + установка сеанса;
- `rpc_handle − tool.duration_ms` = обвязка JSON-RPC;
- `tool_impl − Σ q_*` = слой MCP_Tools_Impl (guidance, запись примеров).

## Изменение семантики duration_ms события инструмента

Результат теперь собирается ДО записи аудита, поэтому `duration_ms` события
`MCP.<tool>.*` включает и сериализацию ответа (раньше она была видна только
разницей с HTTP-слоем). Числа «до/после» публикации сравнивать с этой поправкой.

## Как мерить

```bash
node scripts/mcp_perf_profile.mjs --runs 3
```

Свой запрос/инструмент: `--query "ВЫБРАТЬ ..."` либо `--tool X --args '{...}'`;
режим ответа `--response-mode both|text_only|structured_only`; машиночитаемый
вывод `--json`. При глухом транспорте и живом интернете — ловушка VPN-маршрута,
добавить `--local-address <IP Wi-Fi>` (см. CLAUDE.md «Примечания»).

Скрипт сам связывает слои: запись вызова — точечно по `correlation_id` из
успешного ответа, HTTP-запись — по `request_chars` и порядку следования
(`correlation_id` в ней нет по конструкции). Без прав на журнал регистрации
остаётся клиентский слой + `duration_ms` ответа.

Прогон по живому контуру со СТАРОЙ ревизией (.12.3) законен: скрипт показывает
слои без стадий и честно пишет «стадии не записаны». Проверено 13.08 на
BUH_KORP: клиент 2518 / HTTP 2357 / вызов 2273 / СУБД 8 мс — разрыв ×280 из ТЗ
воспроизведён, инструмент связал все слои ещё до публикации стадий.

## Устойчивость к частичной публикации

Коллектор живёт в MCP_Audit; все обращения из горячих путей — обёртки с
no-op-фолбэком (образец `ТекущиеМиллисекундыUTC`). Сигнатуру
`ОбработатьЗапрос(Текст, Замер)` HTTP-сервис спрашивает пробой
`ПоддерживаетЗамерСтадий`, а не Попыткой вокруг вызова: падение сигнатуры
неотличимо от прикладного исключения, а повтор выполнил бы запрос дважды.
Частичная публикация теряет разбивку, но не запросы. Единственная жёсткая пара —
`MCP_Query` + `MCP_Tools`: `_perf` из результата удаляет только новый MCP_Tools,
старый отдал бы служебный ключ клиенту (правило дописано в манифест, ловится
маркером гейта).

## После публикации (порядок приёмки)

1. `node scripts/mcp_deploy_smoke.mjs --strict-markers` — новый маркер
   «профилирование стадий» проверяет и наличие stages в записи своего вызова,
   и отсутствие `_perf` в ответе.
2. `node scripts/mcp_perf_profile.mjs --runs 3` — водопад стадий появился.
3. Контрольный набор ТЗ (раздел 4) мерить по `duration_ms` события
   `MCP.<tool>.*` с поправкой на сериализацию; разложение постоянной
   составляющей ~340 мс читать из стадий access_check/q_validate/q_setup/
   auth_context/masking, цену R-1 — из `q_ref_presentation_ms` и `q_ref_cells`.
4. Регресс маскирования: 6 путей закрытия `ФизическиеЛица` (§4 ТЗ) — правка
   маскирование не трогала, но stages проходят через тот же СформироватьСообщение.

## Что НЕ сделано (сознательно)

- Оптимизации R-1..R-3 ТЗ — отдельная правка: сначала инструмент, чтобы
  эффект мерился, а не постулировался.
- Глубокие стадии есть только у run_1c_query; отчёты/регистры получают слой
  вызова (access_check…serialize) автоматически, их q_-аналоги добавляются той
  же схемой (`_perf` в результате импл-функции) при необходимости.
