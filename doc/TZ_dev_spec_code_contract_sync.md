## 1. Цель

Восстановить статус `doc/mcp_1c_tools_spec.md` как достоверного контракта для LLM-агентов и интеграторов:

1. Устранить массовые расхождения дефолтов (`include_*`, числовые лимиты) между спекой и кодом (§4, §5).
2. Задокументировать фактически реализованные, но отсутствующие в спеке параметры и поведение (§6).
3. Дописать детальные секции для инструментов, описанных только строкой сводной таблицы (§7).
4. Устранить дефекты кода, выявленные сверкой: мёртвый параметр и утечка внутренних деталей в JSON-RPC ошибках (§8, §9).
5. Закрыть дыры контрактного теста на транспортном уровне и привести артефакты `reports/` в порядок (§10, §11).

## 2. Проблема (факты сверки)

**Ф-6. Дыры и внутренние противоречия самой спеки.**

**Ф-7. Утечка внутренних деталей в JSON-RPC ошибках.** `MCP_JSONRPC.bsl` отдаёт клиенту в `error.data`: для `-32700` — эхо `request_body` и `raw_exception` (JSONRPC:18–22); для `-32603` — `"Internal error: " + ОписаниеОшибки()` плюс `raw_exception` и `params` (JSONRPC:105–110). ## 3. Scope

Входит:

- продуктовое решение по дефолтам и приведение проигравшей стороны (§4, §5);
- ревизия `doc/mcp_1c_tools_spec.md`: дефолты, недокументированные параметры, недостающие секции, внутренние противоречия (§6, §7);
- синхронные точечные правки README (только пункты, где README расходится с принятым решением);
- правки кода: мёртвый параметр (§8), утечка в `error.data` (§9);
- расширение контрактного теста транспортными проверками и версией 2025-11-25 (§10);
- уборка `reports/` (§11).

Не входит:

- изменение состава и семантики самих инструментов (никаких новых tools и полей ответа сверх фиксации фактического поведения);
- переработка протокольных отклонений Ф-8 (unknown tool → -32602, parse error → HTTP 400) — фиксируются в спеке как осознанные отклонения; смена поведения — отдельное ТЗ при необходимости, т.к. затрагивает закреплённые тестами контракты клиентов;
- аудит безопасности за пределами Ф-7;
- сверка полей Output Shape «до последнего ключа» для всех 34 инструментов (выборочная сверка сделана; полная — по мере написания недостающих секций §7).

## 4. Требование F1: решение и выравнивание дефолтов `include_*`

### 4.1. Продуктовое решение (блокирует остальное)

Зафиксировать сторону для каждого флага из таблицы Ф-1. Рабочая гипотеза (рекомендация): **код прав** — дефолты `false` выбраны сознательно ради экономии токенов LLM-агента; спека правится под код. Если для отдельных флагов решение обратное (например, `include_column_types` в `run_1c_query`, без которого агент теряет типы данных) — правится код и `MCP_Tools.bsl` (default в схеме), с прогоном контрактного теста.

### 4.2. Правка спеки

Для каждого флага: `default: true` → `default: false` в inputSchema-блоке секции §7 спеки; в Output Shape пометить соответствующие поля как «возвращается при `include_* = true`». Формулировки вида «по умолчанию возвращает…» в описательном тексте секций привести к фактическому дефолту.

### 4.3. Правка схем кода (независимо от решения)

В `MCP_Tools.bsl` декларировать `default` у всех булевых `include_*` в inputSchema явно (сейчас default не объявлен вовсе — клиент не может узнать дефолт из `tools/list`). Значение — из решения §4.1.

## 9. Требование F6: устранение утечки внутренних деталей в JSON-RPC ошибках (P1)

В `MCP_JSONRPC.bsl`:

1. `-32700` (JSONRPC:18–22): убрать из `error.data` эхо `request_body` и `raw_exception`. Допустимо оставить позицию/краткую причину парсинга без текста исключения платформы.
2. `-32603` (JSONRPC:105–110): убрать `raw_exception` и `params` из `error.data`; текст `message` — нейтральный («Internal error»), без `ОписаниеОшибки()`. Полные детали — только в аудит (`MCP_Audit`, с `correlation_id`), клиенту — `correlation_id` для сопоставления.
3. Выровнять поведение с HTTP-слоем (`MCP_HTTPService.bsl:44–60`), который уже скрывает детали, — единая политика «наружу нейтрально + correlation_id, внутрь аудит полностью».

Тест: негативные проверки в контрактном тесте (битый JSON, спровоцированная внутренняя ошибка) утверждают отсутствие `raw_exception`/`params`/`request_body` в `error.data` и наличие `correlation_id`.

6. заголовок `MCP-Protocol-Version: unsupported-х.х` → HTTP 400 + `-32000`;
7. прогон (или отдельный проход) с `MCP-Protocol-Version: 2025-11-25` — заявленная в README версия должна быть покрыта контрактно.

В спеку — примечания об осознанных отклонениях (Ф-8): unknown tool → tool-level error с HTTP 200; parse error → HTTP 200; поддержка batch как расширение.

## 13. Риски

- **R1.** Смена задокументированных дефолтов (если §4.1 решит в пользу спеки) меняет поведение для существующих клиентов, полагающихся на фактический код. Митигируется тем, что рабочая гипотеза — правка документов, не кода; любые правки кода проходят полный контрактный прогон.
- **R2.** Ужесточение `-32603`/`-32700` (§9) может усложнить отладку интеграторам. Митигируется `correlation_id` в ответе и полными деталями в аудите.
- **R3.** Дописывание 10 секций спеки по коду рискует зафиксировать случайные детали реализации как контракт. Митигируется выверкой каждой секции по фактическому ответу боевого сервера (дампы через `_response_mode=structured_only`) и приёмкой 7.
- **R4.** Добавление `include_auth_context` в каждую inputSchema (§6 п.6) раздувает `tools/list`. Альтернатива (JSON-RPC-параметр `_include_auth_context`) — решить при реализации, зафиксировав выбор в спеке.
- **R5.** Повторный дрейф спеки после ревизии. Митигируется приёмкой 7 (автосверка в CI/контрактном тесте).
