# IMPL: pre-flight валидация полей, табличных частей и псевдонимов в `run_1c_query`

**ТЗ:** `tz_preflight_field_validation.md` (F-01…F-07, ревизия 2026-07-27 — раздел 0 ТЗ)
**ПМИ:** `pmi_preflight_field_validation.md` (T0…T8)
**Затронуто:** `MCP_Metadata.bsl`, `MCP_Query.bsl`, `MCP_Errors.bsl`, `MCP_Tools.bsl`,
`scripts/mcp_contract_test.mjs`, `scripts/required_modules.manifest.json`
**Принцип:** универсальность — состав полей и табличных частей строится из реальной
структуры объекта; в коде нет ни одного имени объекта конкретной конфигурации,
только платформенные имена видов метаданных и служебных подтаблиц.

Продолжение `IMPL_report_preflight_vt_field_validation.md`: тот же барьер, но для
обычных (не виртуальных) таблиц — реквизиты объектов, табличные части, константы.

## Что сделано

### 1. Оракул состава таблицы запроса (`MCP_Metadata.bsl`)

`ПолныйНаборПолейТаблицыЗапроса(ПолноеИмя, ИмяТабличнойЧасти = "")` →
`{ supported, fields, public_fields, reason, table_kind }`. Контракт надмножества и
«никогда не бросает исключение» унаследованы от `ПолныйНаборПолейВиртуальнойТаблицы`.

**Два набора возвращаются раздельно, и это центральное решение:**

| Набор | Назначение | Обработка |
|---|---|---|
| `fields` | оракул существования | полный, необрезанный, **без** фильтра политики доступа |
| `public_fields` | `available_fields`, `did_you_mean` | через `MCP_Security.ПолеРазрешено`, обрезка 40 (30 для ТЧ) |

Причина: фильтр по `allowed` превратил бы скрытое поле в `field_not_found` вместо
`field_not_allowed`, а обрезка по количеству дала бы ложный отказ на реальном поле
«широкого» документа. Существующая `ПоляОбъектаДляДиагностики` делает и то и другое,
поэтому как оракул непригодна и используется по-прежнему только для показа.

Состав набора по видам:

- **Объектные** (`Справочник, Документ, ПланСчетов, ПланВидовХарактеристик, ПланВидовРасчета, ПланОбмена, БизнесПроцесс, Задача`): `СтандартныеРеквизиты` + `Реквизиты` + **имена табличных частей** (это поля-вложенные-таблицы владельца) + **`СтандартныеТабличныеЧасти`** + **`ПризнакиУчета` / `ПризнакиУчетаСубконто`** + короткий платформенный псевдо-список.
- **`РегистрСведений`, `РегистрНакопления`**: `СтандартныеРеквизиты + Измерения + Ресурсы + Реквизиты`, без догадок о `Период`/`Регистратор` (у независимого непериодического регистра их нет).
- **`Константа`** → `{"Значение"}`; это и есть основание F-03.
- **Табличная часть**: `ТЧ.Реквизиты` + `ТЧ.СтандартныеРеквизиты` + **безусловно `Ссылка` и `НомерСтроки`**.
- `supported = Ложь` (проверка не выполняется): `РегистрБухгалтерии`, `РегистрРасчета`, `Перечисление`, стандартные ТЧ, недоступная коллекция `СтандартныеРеквизиты`, пустой набор.

`ТабличныеЧастиТаблицыЗапроса(ПолноеИмя)` → `{ supported, names, standard_names, has_collection, kind, reason }` для F-01 и F-04.
Плюс `ВидПоддерживаетТабличныеЧасти`, `ПлатформенныеПодтаблицыОбъекта`, `НайтиТабличнуюЧастьПоИмени` (без учёта регистра).

### 2. Карта псевдонимов (`MCP_Query.bsl`)

`КартаАлиасовЗапроса(ОчищенныйТекст)` → `{ bindings, sources, conflicts, gave_up, reason }`.
Отличия от `НайтиИсточникиЗапроса`: без дедупликации (она теряет привязку псевдонима к
источнику), с пропуском группы параметров ВТ `(...)`, с полным стоп-списком ключевых слов
(`ЭтоКлючевоеСловоРазделаИсточников`) — базовая `ВыглядитКакАлиасИсточника` при опущенном
`КАК` вернула бы `ЛЕВОЕ` как псевдоним.

`resolution` ∈ `object_table | tabular_part | virtual_table | unresolved`.

**Вся проверка отключается** (`gave_up`) при дисбалансе скобок, отсутствии `ИЗ/FROM` или
отсутствии привязок. **Отдельный псевдоним снимается**, если он привязан к разным
источникам (утечка между пакетами и подзапросами), совпадает с именем временной таблицы,
либо совпадает с именем вида метаданных (иначе `ВЫРАЗИТЬ(… КАК Справочник.Организации)`,
`ССЫЛКА Справочник.X`, `ЗНАЧЕНИЕ(Перечисление.X.Y)` дали бы фантомные «поля»).

### 3. Pre-flight источников и полей (`MCP_Query.bsl`)

`ПроверитьИсточникиИПоляПередВыполнением(ТекстЗапроса, Валидация, КешДиагностики)`
вызывается внутри `ВыполнитьЗапросСОграничениями` после проверки виртуальных таблиц и до
`Запрос.Выполнить()`; флагом `validate_before_run=false` не отключается (о чём в ответе
явное предупреждение). Сбой интроспекции или разбора → warning и деградация на движок.

- **F-01** (`tabular_part_not_found`) отклоняет только при выполнении ВСЕХ условий: ровно 3 сегмента; объект существует и разрешён allowlist; источник не виртуальная таблица; вид ∈ allowlist видов с ТЧ; коллекция `ТабличныеЧасти` прочитана и непуста; третий сегмент отсутствует и в обычных, и в стандартных ТЧ; третий сегмент не в `ПлатформенныеПодтаблицыОбъекта()`.
- **F-02** (`field_not_found`) проверяет только первый сегмент пути после псевдонима; извлечение — существующие `ПоляАдресованныеИсточникуВТ` → `ИзвлечьПоляПоАлиасу`, вызываемые по одному псевдониму, чтобы поле атрибутировалось своей таблице.
- **F-03** — константа: единственное поле `Значение`, фиксированная подсказка.
- Диагностики повторяют форму `СформироватьДиагностикуPreFlightВТ` и добавляют `did_you_mean`, `available_tabular_parts`, `tabular_part`, `alias`.
- Per-request кеш: `table_fields_full:<имя>[.<тч>]`, `tabular_parts:<имя>`.

`ИзвлечьПоляПоАлиасу` дополнена двумя условиями пропуска (`&` перед псевдонимом и
предшествующее `КАК`/`AS`). Обе правки строго сужают набор проверяемых полей, поэтому
безопасны и для существующего пути виртуальных таблиц.

### 4. F-04: коллизия псевдонима с именем табличной части

`ДобавитьПредупрежденияКоллизииПсевдонимаСТабличнойЧастью` вызывается из `Валидировать`
рядом с прочими JOIN-предупреждениями, поэтому бесплатно работает и в `validate_1c_query`,
и на успешном пути `run_1c_query`. Только warning, никогда не блокирует. Дедуп по тройке
(псевдоним, таблица, ТЧ), не более 5 предупреждений.

**Найденный по ходу дефект:** `MCP_Tools.СформироватьОшибкуРезультата` переносил
`validation_warnings` в ответ **только** при наличии `validation_errors`, поэтому на стадии
падения движка предупреждения терялись — ровно там, где F-04 нужнее всего (A-04 требует
warning независимо от исхода). Копирование вынесено из условия; дополнительно
`validation_warnings` добавлены в детали ошибки движка, обоих pre-flight и таймаута.

### 5. F-05: `did_you_mean`

`ВариантыПохожихПолей` переписана: кандидат проходит при расстоянии Левенштейна ≤ 3 **или**
если одно имя является подстрокой другого (это и ловит `Тара` → `ВозвратнаяТара`). Порядок:
префиксные, затем подстрочные, затем по расстоянию; внутри класса — по расстоянию и длине.
Максимум 3. Заведомо далёкое имя даёт пустой список (T7-3).

### 6. F-05.2: одноимённый объект другого вида

`ПодсказкаОбъектаДругогоВида` при `metadata_not_found` проверяет
`Метаданные.НайтиПоПолномуИмени(<Вид> + "." + <Имя>)` по списку платформенных видов
(включая `ФункциональнаяОпция`) и добавляет подсказку в запись ошибки валидации
(`validation_errors[].hint`) и в её текст. Для `Константа.<Имя>` при найденной одноимённой
функциональной опции подсказка дополняется указанием проверить свойство «Хранение».

### 7. F-06: соответствие кода и стадии (`MCP_Errors.bsl`, `MCP_Query.bsl`)

Новый `Код_QueryExecuteError()` → `"query_execute_error"`. На стадии падения движка базовый
код теперь `query_execute_error` (был `internal_error`), диагностики `table_not_found`,
`syntax_imeyuschie`, `grouping_error`, `forbidden_polozhit`, `batch_query_forbidden`,
`vt_param_field_error`, `aggregate_function_name` больше **не** подменяют код на
`query_validation_failed` — это и был дефект падения №4. `field_not_found` и `access_denied`
сохранены. Добавлена страховка: код со словом `validation` на стадии `query_execute`
принудительно заменяется на `query_execute_error`.

**Сужение существующего поведения (следствие отклонения 1 и F-05):** потолок расстояния
Левенштейна сокращает число кандидатов в подсказках виртуальных таблиц. Для
`СуммаОстатокИтого` вместо трёх кандидатов останется `СуммаОстаток` (расстояние до
`СуммаОстатокКт`/`СуммаОстатокДт` больше 3, подстроки нет). Все машинные ассерты прежних
тест-ТЗ выполняются: кандидатов ≤ 3, `СуммаОстаток` присутствует. Подсказки стали короче
и релевантнее — фиксируется как осознанное изменение, а не регресс.

### DEF-01 (T1-4): диагноз протокола неверен, причина глубже

Протокол квалифицировал дефект как «требование F-04 не реализовано». **Это не так.**
Проверено живым вызовом на ЗУП КОРП: `validate_1c_query` для запроса с коллизией псевдонима
возвращает ровно требуемое предупреждение. F-04 работает и универсален.

Настоящая причина — **предсуществующий дефект сериализации деталей ошибки**, не связанный
с этим ТЗ:

1. `MCP_Query.ДиагностикаОшибкиВыполнения` ставит `field`/`field_path`/`object` в `Null`,
   когда имя поля из текста ошибки платформы не извлекается.
2. Текст «Неоднозначное поле» не распознавался, а `ОбъектДляДиагностикиПоля` не разрешает
   объект для псевдонима-коллизии → в детали попадает `Null`.
3. `MCP_Errors.ДеталиВСтроку` вызывал `ЗаписатьJSON` **напрямую**, без
   `MCP_JSONRPC.ПодготовитьКЗаписиJSON` — а эта подготовка существует именно для конвертации
   `Null` → `Неопределено`.
4. `ЗаписатьJSON` падал на `Null`, срабатывал фоллбек `Строка(Детали)`, и весь блок деталей
   молча превращался в строку «Структура».

Подтверждено сравнением двух ошибок движка на одной базе: без коллизии детали полные
(`hint`, `available_fields`, `platform_message`, `field`, `suggestions`,
`validation_warnings`), с коллизией — `parsed_details: {raw: "Структура"}` и ничего больше.
Дефект гасил детали при **любой** ошибке движка с неразобранным именем поля; предупреждение
F-04 было лишь первым, чьё отсутствие заметили.

**Правки:**
- `MCP_Errors.ДеталиВСтроку` использует `MCP_JSONRPC.СохранитьJSON` (та же подготовка,
  фоллбек сохранён).
- `ДиагностикаОшибкиВыполнения` распознаёт «Неоднозначное поле»: новый вложенный
  `error_code = "ambiguous_field"`, извлечение пути поля (больше не `Null`) и подсказка,
  что поле существует, а переименовать нужно псевдоним, со ссылкой на `validation_warnings`.
  Верхнеуровневый код для этого случая — `query_execute_error` по правилу F-06.3;
  прежний `field_not_found` был дезинформацией, поле существует.

### DEF-02 (T7-2): произвольный порядок и усечение набора полей

`available_fields` содержал ровно 30 имён, среди которых не было реально существующих
`Количество` и `Номенклатура`. Причина: оракул строил `fields` обходом `Соответствие`, то есть
в произвольном порядке, а проекция усекала до 30 — срез получался случайным подмножеством.
`did_you_mean` искал кандидатов по этому же усечённому списку, поэтому не находил исправление
даже при расстоянии 1. Видно в живом ответе: `Ссылка, НомерСтроки, ИсходныйДокумент, …` —
ни алфавит, ни порядок конфигурации.

**Правки:**
- Оракул ведёт параллельный массив `Порядок` — порядок метаданных (реквизиты сначала);
  `Соответствие` остаётся только дедупликацией. Базовые `ДобавитьПолеВНабор` /
  `ДобавитьИменаКоллекцииВНабор` не тронуты — их использует генератор полей ВТ.
- `public_fields` больше не усекается: он же питает `did_you_mean`.
- Усечение только для показа, в одном месте (`ОграничитьСписокПолейДляПоказа`, предел 80),
  плюс новые поля ответа `available_fields_total` и `available_fields_truncated` — обрезка
  перестала быть молчаливой.

## Границы

- Глубокое разыменование (`Т.Ссылка.Контрагент.ИНН`) не валидируется — проверяется только первый сегмент; требует резолва типов.
- Неквалифицированные поля (без псевдонима) вне объёма F-02; для виртуальных таблиц они по-прежнему обрабатываются своей проверкой.
- Семантика типов и совместимость агрегатов не проверяются.
- **Обнаруженный дефект вне объёма (1):** `КаноническийВидМетаданных` не знает `ЖурналДокументов`, `КритерийОтбора`, `Последовательность` и английских синонимов видов, поэтому такие источники уже сегодня получают ложный `unknown_query_source` от `Валидировать`. Новый код их только пропускает, дефект не усугубляет и не лечит — нужна отдельная задача.
- **Обнаруженный дефект вне объёма (2): агрегатная таблица `Константы`.** Помимо `Константа.<Имя>` платформа предоставляет единую таблицу `Константы`, где поля — имена всех констант конфигурации. Форма подтверждена живым вызовом на БП КОРП (27.07.2026): `ВЫБРАТЬ Константы.ВедетсяУчетВозвратнойТары ИЗ Константы КАК Константы` → 1 строка, значение «Да». Через `run_1c_query` она **сегодня недоступна**: у токена `Константы` нет точки, `ПолноеИмяМетаданныхИзЛексемы` возвращает пустое имя, и `Валидировать` отклоняет источник как `unknown_query_source` до движка. Это существующее поведение, не следствие настоящей правки: новый pre-flight такой источник корректно пропускает (`resolution = unresolved`). Поддержка требует особого случая в разрешении источников; составом полей естественно взять имена всех констант — это заодно даёт полноценный оракул для F-02 по этой таблице.
