## 1. Цель

Устранить три расхождения между реализацией pre-flight валидации полей ВТ и требованиями тест-ТЗ, выявленные на live-прогоне, не нарушив действующие гарантии (ноль ложных отказов; запрос не доходит до движка при доказанно-битом поле):

1. **F4-fix. Валидация неквалифицированных полей.** Pre-flight должен отсекать несуществующее поле ВТ и тогда, когда оно записано без алиаса источника (`ВЫБРАТЬ СуммаОстатокИтого ИЗ …Остатки(…)`), — при условии единственного источника-ВТ.
2. **F5-fix. Точность генератора для `ОборотыДтКт`.** Убрать «фантомные» поля `СуммаОборотДт`/`СуммаОборотКт` (и аналогичные для других балансовых ресурсов), которых нет в реальной ВТ и которые движок отклоняет.
3. **F6-fix. Диагностический warning.** При `validate_before_run=false` и сработавшем pre-flight явно сообщать, что флаг проигнорирован.

Плюс раздел требований к тестовой инфраструктуре (§8), закрывающий незакрытые на retest группы TG-5, TG-6, TG-10 и контрактный прогон.

## 2. Проблема (факты retest)

**Замечание 1 (Middle).** `ПоляАдресованныеИсточникуВТ` (`MCP_Query.bsl`, ~2478) извлекает только конструкции `Алиас.Поле` (процедура `ИзвлечьПоляПоАлиасу`, шаблон `ВРег(Алиас) + "."`). Неквалифицированный токен в разбор не попадает.

- `ВЫБРАТЬ Т.СуммаОстатокИтого ИЗ …Остатки(&Период) КАК Т` → `error_code=validation_failed_before_run`, движок не вызван (корректно).
- `ВЫБРАТЬ СуммаОстатокИтого ИЗ …Остатки(&Период)` → доходит до движка, `error_code=field_not_found` с `platform_message` (пост-error).

Негативы N-01…N-04 в тест-ТЗ записаны **без** алиаса ⇒ в буквальном виде Exit-критерий 1 (§9 тест-ТЗ) не выполняется.

**Замечание 2 (Low).** `MCP_Metadata.bsl`, блок `ОборотыДтКт` в `ЗаполнитьПоляВТБухгалтерии` (~791–806):

```bsl
Для Каждого П Из ПрефиксыБаланс Цикл          // {Сумма}
    ДобавитьПолеВНабор(Набор, П + "Оборот");    // СуммаОборот — верно
КонецЦикла;
Для Каждого П Из ПрефиксыСумм Цикл             // {Сумма, ВалютнаяСумма, Количество, +НУ/ПР/ВР}
    ДобавитьПолеВНабор(Набор, П + "ОборотДт");   // при П="Сумма" → СуммаОборотДт (ФАНТОМ)
    ДобавитьПолеВНабор(Набор, П + "ОборотКт");   // при П="Сумма" → СуммаОборотКт (ФАНТОМ)
КонецЦикла;
```

Второй цикл идёт по всем суммовым префиксам, включая балансовый «Сумма». У балансового ресурса в `ОборотыДтКт` Дт/Кт-оборота не существует (сумма корреспонденции одна). Live: движок отклоняет `Т.СуммаОборотДт` для `ОборотыДтКт` как `field_not_found`. Тот же дефект — в инварианте `qa/golden_virtual_table_fields.md` и в оракуле P-04 тест-ТЗ.

**Замечание 3 (Low).** При `validate_before_run=false` pre-flight корректно продолжает блокировать битое поле (security не обходится), но ожидаемого тест-ТЗ (TG-9/S-01) warning «validate_before_run=false проигнорирован» в `warnings[]` нет.

## 3. Scope

Входит:

- расширение pre-flight на неквалифицированные поля при единственном источнике-ВТ (§4);
- корректировка генератора `ОборотыДтКт` (§5);
- добавление warning при игнорировании `validate_before_run=false` (§6);
- синхронная правка `qa/golden_virtual_table_fields.md` и оракула P-04 в `TZ_test_preflight_vt_field_validation.md`;
- контрактные и регрессионные проверки на изменённое поведение;
- раздел требований к тест-инфраструктуре (§8).

Не входит:

- валидация неквалифицированных полей при JOIN нескольких источников (≥2 источника) — вне текущей итерации;
- проверка неквалифицированных полей в секциях, отличных от `ВЫБРАТЬ` (см. §4.4 — расширяемость на будущее);
- проверка типов выражений и совместимости агрегатов (как и в базовом ТЗ, вне scope);
- поля основной (невиртуальной) таблицы регистра.

## 4. Требование F4-fix: валидация неквалифицированных полей

### 4.1. Условие активации

Проверка неквалифицированных полей выполняется **только** если в запросе (на уровне разбираемого запроса; подзапросы рассматриваются как отдельные области) ровно **один** источник и это источник-ВТ с `supported = Истина`. При двух и более источниках неквалифицированные поля НЕ проверяются (остаётся текущее поведение — только `Алиас.Поле`).

### 4.2. Извлечение кандидатов из списка `ВЫБРАТЬ`

Разбирается фрагмент между `ВЫБРАТЬ` (с учётом `ВЫБРАТЬ РАЗЛИЧНЫЕ` / `ПЕРВЫЕ N`) и ближайшим `ИЗ` верхнего уровня. Список делится по запятым верхнего уровня (не внутри скобок). Из каждого элемента выделяется ведущий идентификатор-поле.

### 4.3. Правило безопасности (обязательное)

Если токен нельзя **уверенно** классифицировать как ссылку на поле — он **пропускается** (запрос уходит на движок), отказ не выдаётся. Это сохраняет гарантию «ноль ложных отказов» (блокер §9). Не считаются полем и не отклоняются:

- ключевые слова языка запросов (`ВЫБОР`, `КОГДА`, `ЕСТЬNULL`, `ВЫРАЗИТЬ`, `КАК`, `РАЗЛИЧНЫЕ`, `ПЕРВЫЕ`, и т.п.);
- вызовы функций/агрегатов (идентификатор, за которым идёт `(` — `СУММА(...)`, `КОЛИЧЕСТВО(...)`, `ПРЕДСТАВЛЕНИЕ(...)`, `ЕСТЬNULL(...)`);
- параметры запроса (`&Имя`);
- выходные алиасы (то, что идёт после `КАК` в элементе списка) — проверяется **входное** поле, не алиас;
- разыменование `Идент.Идент…` — это уже квалифицированная форма, обрабатывается существующей веткой; неквалифицированной проверке подлежит только одиночный идентификатор без точек;
- строковые/числовые литералы, `NULL`, `ИСТИНА`/`ЛОЖЬ`, `ЗНАЧЕНИЕ(...)`;
- элементы, содержащие любые операторы/выражения (`+`, `-`, `*`, `/`, скобки, сравнения) — в первой итерации такие элементы целиком пропускаются (не вычленяем поля из выражений).

То есть отклонению подлежит только «чистый» одиночный идентификатор-поле в элементе списка `ВЫБРАТЬ`.

### 4.4. Расширяемость

Экстрактор реализовать так, чтобы источник секций был параметризуем (в первой итерации — только список `ВЫБРАТЬ`), с возможностью позже добавить `ГДЕ`/`УПОРЯДОЧИТЬ ПО`/`СГРУППИРОВАТЬ ПО`/`ИМЕЮЩИЕ` без переписывания ядра. Расширение секций — вне текущего scope.

### 4.5. Формат отказа

Идентичен текущему pre-flight-отказу: `error_code=validation_failed_before_run`, `available_fields`, `available_fields_source="virtual_table"`, `source_table`, `field`, `hint` (имя поля + «не существует» + ≤3 Левенштейн-кандидата), `suggestions` с формулировкой «движок 1С не вызывался». Движок не вызывается.

### 4.6. Точка встраивания

В `ПроверитьПоляВиртуальныхТаблицПередВыполнением` (`MCP_Query.bsl`, ~2384): после сбора `АдресованныеПоля` для источника, если выполнено условие §4.1 (единственный источник-ВТ), дополнить множество проверяемых полей неквалифицированными кандидатами из §4.2–4.3. Существующая логика `Алиас.Поле` и деградация `supported=false` (F-04) не меняются.

## 5. Требование F5-fix: точность генератора `ОборотыДтКт`

### 5.1. Изменение

В `ЗаполнитьПоляВТБухгалтерии` (`MCP_Metadata.bsl`, блок `ОборотыДтКт`) цикл добавления `ОборотДт`/`ОборотКт` должен идти по суммовым префиксам **за вычетом** балансовых. Балансовый ресурс («Сумма») получает только `{П}Оборот`; небалансовые (`ВалютнаяСумма`, `Количество`, и `{база}{НУ|ПР|ВР}`) — только `{П}ОборотДт` и `{П}ОборотКт`.

Ожидаемый результат для `РегистрБухгалтерии.Хозрасчетный.ОборотыДтКт`:

- присутствуют: `СуммаОборот`, `ВалютнаяСуммаОборотДт/Кт`, `КоличествоОборотДт/Кт`, `СуммаНУОборотДт/Кт`, `СуммаПРОборотДт/Кт`, `СуммаВРОборотДт/Кт` и т.д.;
- отсутствуют (устраняется): `СуммаОборотДт`, `СуммаОборотКт`.

### 5.2. Инвариант надмножества

Набор обязан оставаться ⊇ реальных колонок ВТ. Удаляются только заведомо несуществующие поля балансового ресурса; это не создаёт риска ложных отказов (у балансового ресурса Дт/Кт-оборота в `ОборотыДтКт` не бывает по устройству платформы). Реализация не должна опираться на строковое имя «Сумма»: балансовость определяется через `БалансовыеПрефиксыБухгалтерии(ОМД)` (уже существует), чтобы сохранить универсальность (кастомный балансовый ресурс — R1).

### 5.3. Синхронные правки (в этом же ТЗ)

- `qa/golden_virtual_table_fields.md`: из инварианта `ОборотыДтКт ⊇ { … }` убрать `СуммаОборотДт`, `СуммаОборотКт`; в anti-union добавить явную проверку `СуммаОборотДт ∉ set` и `СуммаОборотКт ∉ set`.
- `TZ_test_preflight_vt_field_validation.md`, оракул P-04: заменить `СуммаОборотДт, СуммаОборотКт, ВалютнаяСуммаОборотДт` на реальные поля `ОборотыДтКт` (например `СуммаОборот, ВалютнаяСуммаОборотДт, КоличествоОборотДт`).

## 6. Требование F6-fix: warning при `validate_before_run=false`

Если pre-flight сработал (обнаружено битое поле ВТ) при переданном клиентом `validate_before_run=false`, в `warnings[]` результата добавить сообщение:

> «validate_before_run=false проигнорирован: pre-flight-проверка полей виртуальных таблиц обязательна и не отключается флагом.»

Само поведение блокировки (A-01: флаг не обходит проверку) не меняется. Сообщение добавляется только в сценарии, когда флаг фактически проигнорирован (т.е. был передан `false` и pre-flight дал отказ).

## 7. Критерии приёмки

1. **F4-fix / TG-1.** Все четыре негатива N-01…N-04 в буквальной (неквалифицированной) форме из тест-ТЗ дают `validation_failed_before_run`; движок не вызван (нет `platform_message`, есть «движок 1С не вызывался»); `available_fields` непустой; кандидатов ≤ 3.
2. **F4-fix / регресс.** Квалифицированная форма `Алиас.Поле` работает как прежде; поведение при `supported=false` (F-04, warning без отказа) не изменилось.
3. **F4-fix / отсутствие ложных отказов.** На наборе валидных запросов (в т.ч. с функциями/агрегатами/выражениями/выходными алиасами/параметрами в списке `ВЫБРАТЬ`, при единственном источнике-ВТ) — **ноль** отказов pre-flight. Неуверенные токены уходят на движок.
4. **F4-fix / JOIN.** При двух и более источниках неквалифицированные поля не проверяются (нет отказа), квалифицированные — проверяются по своему источнику.
5. **F5-fix.** Генератор для `ОборотыДтКт` не содержит `СуммаОборотДт`/`СуммаОборотКт`; содержит `СуммаОборот`, `ВалютнаяСуммаОборотДт/Кт`, `КоличествоОборотДт/Кт`, `Сумма{НУ|ПР|ВР}ОборотДт/Кт`. Живой запрос `Т.СуммаОборот` к `ОборотыДтКт` выполняется; набор остаётся ⊇ реальных колонок.
6. **F5-fix / синхронность.** `qa/golden_virtual_table_fields.md` и оракул P-04 в тест-ТЗ приведены в соответствие; контрактная проверка `tool.vt_field_generator_authoritative_superset` зелёная.
7. **F6-fix.** При `validate_before_run=false` и битом поле в `warnings[]` присутствует сообщение об игнорировании флага; блокировка сохраняется.
8. **Паритет (F-07/F-08).** `available_fields` в pre-flight-отказе и `common_fields` из метаданных остаются идентичными и после правок §5.
9. **Контрактный прогон** `mcp_contract_test.mjs --all-response-modes` зелёный во всех трёх режимах ответа; артефакт приложен.

## 8. Требования к тестовой инфраструктуре (закрытие TG-5, TG-6, TG-10, контракт)

- **TG-6 (локаль).** Добавить юнит/контрактную проверку, что путь pre-flight-отказа формирует `available_fields` из генератора (`available_fields_source="virtual_table"`) и НЕ вызывает разбор текста ошибки платформы (`ИзвлечьПолеИзОшибкиПлатформы`). - **Контракт.** Прогон `node scripts/mcp_contract_test.mjs --all-response-modes --out reports/preflight_vt_retest.json --verbose` с кредами `MCP_BASIC`; приложить `reports/preflight_vt_retest.json`.

## 9. Риски

- **R1 (F4-fix).** Ложный отказ на валидном неквалифицированном выражении из-за ошибочной классификации токена. Митигируется правилом §4.3 «при неуверенности — пропускать» и приёмкой 3.
- **R2 (F4-fix).** Неверное определение «единственного источника» при подзапросах/временных таблицах. Митигируется тем, что условие §4.1 проверяется на уровне разбираемого запроса, а подзапросы уже отсекаются существующим разбором источников; добавить кейсы с подзапросом (регресс E-02).
- **R3 (F5-fix).** Гипотетическая конфигурация с балансовым ресурсом, имеющим Дт/Кт-оборот в `ОборотыДтКт`. Оценивается как несуществующий на практике; балансовость определяется через `БалансовыеПрефиксыБухгалтерии`, а не хардкод «Сумма».
- **R4.** Расхождение golden ↔ реализация после правок. Митигируется приёмкой 6 и контрактной проверкой суперсета.

## 10. Границы

- Только источник-ВТ; поля основной таблицы регистра — отдельное ТЗ.
- Неквалифицированные поля — только при единственном источнике и только в списке `ВЫБРАТЬ` (расширение секций/JOIN — будущие итерации).
- Типы выражений и совместимость агрегатов не проверяются.
- TOP-0 compile-probe не используется (детерминизм/локале-независимость, A-05 базового ТЗ).
