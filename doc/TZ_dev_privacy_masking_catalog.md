## 1. Задача

**Политика маскирования — данные, а не код.** Сейчас состав маскируемого задаётся тремя способами сразу: секцией `privacy` JSON-константы `MCP_ServerConfig`, зашитыми в код списками типов персон/организаций и зашитым списком их чувствительных полей. Переносим всё в одно место — предопределённый элемент справочника `MCP_Маскирование`, реквизит `Значение` (строка неограниченной длины) с JSON-политикой. Пользователь задаёт состав галками в обработке; код только применяет то, что записано.

Три принципа:

- **Движок остаётся, состав уходит.** Механика подмены (второй эшелон, пометка колонок, идемпотентность, различимость кодов P-0c) не меняется. Меняется источник ответа на вопрос «что маскировать» и удаляется вся логика, которая отвечала на него из кода.
- **Fail-closed сохраняется.** Рубильник включён + политика нечитаема (битый JSON, недоступен справочник) = аварийный режим с максимальной маской, как сейчас при битой константе (R-6). Отказов инструментов нет ни в одной форме.
- **Выключенный рубильник — осознанное решение.** `privacy.enabled = false` в `MCP_ServerConfig` отключает применение маскирования целиком; это административный акт, а не деградация. Отсутствие ключа, секции или самой константы трактуется как `Истина` (отсутствие рубильника не отключает защиту).

`MCP_ServerConfig` продолжает обслуживать всё остальное: `limits`, `http`, `web_client`, query_examples и т.д. Константа `MCP_Allowlist` не затрагивается. Новых констант не добавляется.

## 3. Новые объекты метаданных

Новых объектов два: справочник и обработка. Рубильник новым объектом не является — это ключ в существующей константе (§3.2).

### 3.1. Справочник `MCP_Маскирование`

- Без иерархии, без владельцев, длина наименования стандартная, код — по умолчанию.
- Реквизит **`Значение`** — Строка, **неограниченная длина** (0), многострочная.
- Предопределённый элемент **один**: **`НастройкиМаскирования`** — действующая политика, единственный источник для движка (постановка заказчика: «все данные по маскированию хранятся в одном предопределённом элементе»).
- Права: чтение/запись — только административная роль. Движок читает политику **в привилегированном режиме** (M-3), поэтому права и RLS сервисного пользователя на защиту не влияют.

**Почему одного элемента достаточно** (уточнение 11.08). В редакции 1.2.0 был второй элемент — «эталон» под кнопку «Настройки по умолчанию». Он не нужен, потому что у политики маскирования нет понятия «значение по умолчанию»:

- в заготовке SDCH эта кнопка означала «вернуть то, что задано в конфигураторе» — там был внешний источник истины (флаги истории данных у объектов метаданных). У политики маскирования такого источника нет: единственный источник — то, что записал администратор;
- роль «внешнего источника истины» на время внедрения играет `MCP_ServerConfig`, и обращение к нему — это ровно команда «Импортировать из MCP_ServerConfig» (§7.1). Две кнопки означали одно и то же действие, поэтому остаётся одна;
- «пустая политика» как дефолт уже доступна кнопкой «Очистить всё»;
- если администратору нужен снимок перед правкой, справочник это позволяет без кода: **обычные** (непредопределённые) элементы служат именованными копиями, движок читает только предопределённый. Плюс поле предпросмотра JSON, откуда текст копируется куда угодно.

Итог: элемент один, кнопка «Настройки по умолчанию» удаляется (А.4), команда импорта остаётся.

### 3.2. Рубильник: ключ `privacy.enabled` в существующей константе `MCP_ServerConfig`

**Новая константа не создаётся** (уточнение заказчика 11.08: «константа же уже есть в MCP-сервере»). Рубильник — булев ключ `privacy.enabled` в уже существующей константе `MCP_ServerConfig`, той самой, где сегодня лежат `type_field_masks` и остальной состав политики:

```json
"privacy": { "enabled": true }
```

После переезда секция `privacy` в `MCP_ServerConfig` сохраняется, но **только с этим одним ключом**; состав политики (`masked_fields`, `type_aliases`, `type_field_masks`, `publish_details`, упразднённые режимы) уходит в справочник, и оставленные там ключи состава дают предупреждение M-12.

Почему рубильник живёт именно здесь, а не в справочнике рядом с политикой:

- это **серверная настройка уровня контура**, того же класса, что `limits` и `http` — по правилу проекта такие вещи меняются константой без публикации кода;
- **аварийный выход не должен лежать внутри того, что сломалось.** Если JSON справочника испорчен, движок уходит в аварийный режим с максимальной маской; администратору нужен способ выключить маскирование, не восстанавливая сперва испорченный артефакт. Рубильник в другом хранилище это обеспечивает — а именно такой сценарий у проекта уже случался дважды за волну 2;
- обратная связка тоже безопасна: сломанный JSON `MCP_ServerConfig` не мешает читать политику справочника, а `МаскированиеВключено()` при нечитаемой настройке возвращает `Истина`.

Семантика чтения (функция `МаскированиеВключено()`, M-4): ключа нет → `Истина`; секции `privacy` нет → `Истина`; константа отсутствует или нечитаема → `Истина`. Fail-closed: выключить защиту может только явно записанная `false`.

Обработка рубильник **не пишет** — она его только показывает (А.5): переписывание `MCP_ServerConfig` из формы означало бы риск повредить `limits`/`http` вместе с сервером. Переключение — правка константы администратором, как сегодня меняются лимиты.

### 3.3. Обработка `MCP_MaskingRule`

**Объект расширения MCP** — ветка «Обработки», рядом со справочником и константами (решение заказчика 12.08.2026; редакции до 1.6.0 допускали параллельный внешний вариант — он упразднён). Следствия:

- блок регистрации дополнительной обработки БСП (`СведенияОВнешнейОбработке`) и его обвязка **удалены** из модуля объекта — у объекта расширения механизм не используется; обработка открывается через «Все функции» или командой интерфейса;
- форма зовёт `MCP_Config` **напрямую** — индирекция «поиск модуля по имени» с ветками «расширение не подключено» существовала только ради внешнего варианта; прямые вызовы к тому же видны чекеру межмодульных связей (`bsl_cross_module_calls`);
- диагностика «движок не читает справочник» из отчёта записи удалена: обработка приезжает только вместе с модулями расширения, рассинхрон «обработка новая — движок старый» исключён поставкой, а несовпадение версий валит компиляцию модуля формы громко, не молча. Ревизия движка в отчёте остаётся;
- быстрый перенос уже собранной формы: в конфигураторе ПКМ на ветке «Обработки» расширения → «Вставить внешнюю обработку, отчёт…» → выбрать .epf — форма с реквизитами, элементами, условным оформлением и привязками событий импортируется целиком; затем заменить оба модуля текстами из репозитория и удалить внешнюю обработку (и её подключение в «Дополнительных отчётах и обработках», если было).

Спецификация — §6. В репозитории код лежит в `src/DataProcessors/MCP_MaskingRule/` (модуль объекта + модуль формы); пути в охвате `scripts/bsl_predeploy_check.mjs` и `scripts/required_modules.manifest.json` (M-19).

## 4. Канон JSON в реквизите `Значение`

```json
{
  "privacy": {
    "masked_fields": ["ИНН", "КПП"],
    "type_aliases": [
      { "type": "Справочник.Контрагенты", "prefix": "Контр-" },
      { "type": "Справочник.Проекты", "prefix": "Проект-" },
      { "type": "РегистрСведений.ДокументыФизическихЛиц", "prefix": "ДокФЛ-" }
    ],
    "type_field_masks": [
      { "type": "Справочник.Проекты", "fields": ["Наименование", "Код", "Руководитель"] },
      { "type": "Справочник.Контрагенты", "fields": ["НаименованиеПолное", "Телефон"] }
    ],
    "publish_details": true
  }
}
```

Правила (M-1):

- Корень содержит объект `privacy` — форма секции сохранена, семантика разбора (нормализация имён, warnings/errors, аварийный режим) — та же, что у сегодняшних читателей `ПсевдонимыТиповLLM`/`МаскиПолейТиповLLM`/`ПоляМаскированияLLM`. Меняется только источник текста.
- **Пустое `Значение`** (или пустой `privacy`) = пустая политика: маскирования нет, `enabled=false`, ошибок нет. Это законное состояние «ничего не настроено».
- **Синтаксически битый JSON** = аварийный режим: максимальная маска, причина в `privacy.config_errors`, инструменты работают (перенос R-6 на новый источник).
- Ключи `organization_aliases` / `person_aliases` **упразднены**: читателей нет. Если ключ встречен — предупреждение в `config_warnings`: «ключ упразднён, записи не применяются; используйте type_aliases/type_field_masks» (M-2). Молча игнорировать нельзя — это признак недоехавшей миграции.
- Прочие неизвестные ключи внутри `privacy` — предупреждение (как сейчас), движком не применяются, обработкой при перезаписи **сохраняются** (§6.5).
- Записи `type_field_masks` могут нести дополнительные ключи-массивы (`core_whitelist_foreign` и т.п., см. комментарий перед `МаскиПолейТиповLLM`, `MCP_Config.bsl:843`) — обработка их не редактирует, но обязана сохранять в записи при перезаписи (M-14).

## 5. Изменения серверного кода

### 5.1. `MCP_Config.bsl` — источник политики

Новое:

- **M-3** `ТекстПолитикиМаскирования()` — возвращает `Значение` предопределённого элемента `НастройкиМаскирования` справочника `MCP_Маскирование`. Чтение в привилегированном режиме. Справочник не найден в конфигурации или элемент недоступен → исключение (это и есть сигнал аварии для читателей секций — см. ниже). Пустое значение → пустая строка без исключения.
- **M-4** `МаскированиеВключено()` — читает ключ `privacy.enabled` из существующей `MCP_ServerConfig` штатной обвязкой (`НастройкиСервера()` → `ЗначениеJSON(Privacy, "enabled", Истина)` → `БулевоИзЗначения(…, Истина)`), в `Попытке`. Ключа/секции/константы нет или JSON нечитаем → `Истина`. Новых констант не заводится (§3.2). Функция обязана быть дешёвой и не обращаться к справочнику: её зовёт `МаскироватьПоляДляLLM` на каждое значение (M-15).

Переключение источника:

- **M-5** `СекцияPrivacy(ИмяСекции)` (`MCP_Config.bsl:1226`) — вместо `НастройкиСервера()` разбирает `ТекстПолитикиМаскирования()`. КРИТИЧНО: сохранить контракт «исключение наружу = авария» — комментарий перед `PrivacyPublishDetails` (`MCP_Config.bsl:1206-1215`) остаётся в силе: ни `СекцияPrivacy`, ни новый источник оборачивать в `Попытку` нельзя, читатели секций опознают аварию именно по исключению.
- **M-6** `ПоляМаскированияLLM()` (`MCP_Config.bsl:151`) — читает `masked_fields` через `СекцияPrivacy`; fallback `llm_masked_fields` из корня server-config (`MCP_Config.bsl:163-166`) удаляется.
- **M-7** `ЕстьПризнакDenyВНастройкахPrivacy()` (`MCP_Config.bsl:1701`) — дешёвый поиск подстроки `deny` выполняется по тексту политики справочника, не по константе. Первой строкой: рубильник выключен → `Ложь`. Семантика ошибок прежняя (нечитаемо → `Истина`, пропуск на точную проверку).
- **M-8** `PrivacyPublishDetails()` — без изменений по коду (читает через `СекцияPrivacy`), источник сменится автоматически.

Упразднение режимов:

- **M-9** Удалить: `ПсевдонимыОрганизацийLLM` (`:344`), `ИнформацияПсевдонимовОрганизацийLLM` (`:386`), `ПсевдонимыПерсонLLM` (`:402`, включая зашитый список чувствительных полей `:412-421`), `ИнформацияПсевдонимовПерсонLLM` (`:459`), `НепустойПрефиксПсевдонима` (`:478`, если других вызовов не останется).

## 6. Обработка `MCP_MaskingRule`

### 6.1. Что берём из заготовки, что выбрасываем

Заготовка — форма настройки «Истории данных» (SDCH). Берём композицию и скелет процедур:

- два дерева: слева «Объекты метаданных» (вид → объект), справа «Поля и табличные части» текущего объекта (группа → поле), с поиском по обоим;
- трёхсостоянные пометки (0/1/2) с агрегатами вверх/вниз — процедуры `ЗагрузитьМетаданныеВДеревоМетаданных` (`:61`), `ЗаполнитьРеквизитыДереваМетаданных` (`:715`), конструкторы деревьев `НовоеДеревоМетаданных` (`:1438`), `РеквизитыДереваМетаданных` (`:1461`), `СоответствиеРеквизитовИНомерКартинки` (`:1037`);
- обход групп `Реквизиты`, `СтандартныеРеквизиты`, `Измерения`, `Ресурсы`, `РеквизитыАдресации`, `ПризнакиУчета`, `ТабличныеЧасти`, `СтандартныеТабличныеЧасти`.

Выбрасываем целиком (заказчик 11.08: шаблон корректируем свободно):

- всю интеграцию с `ИсторияДанных.*` (`ПолучитьНастройки` / `УстановитьНастройки` / `УдалитьВерсии`), семантику `ВключеноВКонфигураторе` и `ИспользованиеПолей`;
- область `ОчисткаИстории` (форма прогресса, выбор даты, фоновые шаги) и кнопку «Очистить историю»;
- отладочную область и вызовы отсутствующих у нас методов объекта (`ЭтотОбъект().СписокОбъектовМетаданных`, `ЭтотОбъект().ИзменениеПометки`, `ТекущаяВерсияПлатформы`) — заменяются собственными реализациями в модуле объекта обработки.

Переименовываем всё под проект (**M-25**, решение заказчика 5):

- имена процедур, функций и переменных, отражающие историю данных (`НастройкиИсторииДанных`, `ЗаписатьНастройкиИсторииДанных`, `СброситьНастройкиУОбъекта`, `ИспользованиеИсторииДанныхВключено` и т.п.), заменяются терминами маскирования (`ПолитикаМаскирования`, `ЗаписатьПолитикуМаскирования`, …);
- заголовок формы, синонимы и подсказки элементов, тексты вопросов и сообщений — про маскирование; конструкции `НСтр` с кодами `SYS='SDCH.*'` заменяются простыми строками проекта;
- комментарии и имена областей (`#Область …`) переписываются по фактическому содержанию; упоминаний «истории данных» в них не остаётся;
- **лицензионная шапка и упоминание происхождения удалены** (правка 11.08 по решению заказчика; в редакции 1.4.0 требовалось обратное). Основание: оба модуля написаны заново, а последний дословно перенесённый фрагмент — каскад пометок `ИзменениеПометки`/`ПроставитьПометкиВниз`/`ПроставитьПометкиВверх` — удалён вместе с переходом правой панели на Булево. Остаток общего с заготовкой (`СведенияОВнешнейОбработке` и обвязка `ПодсистемаСуществует`/`ОбщийМодуль`/…) — не оригинальный код заготовки, а стандартный шаблон БСП для автономных обработок, опубликованный 1С. Вместо шапки — обычный комментарий-описание модуля.
- **Если в модули вернётся дословный код заготовки** (например каскад пометок), лицензионное уведомление MIT обязано вернуться вместе с ним: MIT требует сохранять уведомление в копиях и существенных частях. Это правило сопровождения, а не разовая правка.

Проверка M-25 офлайн: поиск по модулям обработки подстрок `ИсторияДанных`, `ИсторииДанных`, `SDCH` не находит ничего.

### M-26. Пометка имени персоны закрывает класс имени объекта (ревизия `2026-08-11.3`)

Живой замер трёх контуров 11.08 (после деплоя каталога): политика
`ФИО, Фамилия, Имя, Отчество, ИНН, СНИЛС` у `Справочник.ФизическиеЛица` отдавала
**ФИО открытым** сразу тремя каналами — колонкой `Наименование`, выражением
`ПРЕДСТАВЛЕНИЕ(Ссылка)` и ключом `presentation` внутри структуры ссылки. Причина:
признак `mask_presentation` поднимался только полем роли «имя объекта»
(Наименование, НаименованиеПолное, КраткоеНаименование, Код), а у `ФИО` роль
«имя_персоны» и в триггер она не входила. Администратор пометил имя человека и
получил ложное чувство защиты — тот же класс дефекта, что дважды откатывал волну 2.

Требование: у записи `type_field_masks` появляется второй признак
**`mask_person_name`** (поднимается полем роли «имя_персоны»), и он закрывает
**весь класс имени объекта** — `Наименование`, `НаименованиеПолное`,
`КраткоеНаименование`, `ФИО`, `Представление`/`presentation`. `Код` в класс НЕ
входит: он не имя, а стабильный идентификатор, и через него держится различимость
обезличенных строк.

Правило односторонее: пометка `Наименования` НЕ закрывает `ФИО` — это отдельный
реквизит и метится отдельно.

Псевдониму типа производное закрытие **не уступает**, хотя код различим, а `XXXXXXX`
склеивает всех в одного. Уступка означала бы, что колонку не метит гейт запроса, и
тогда подстановка кода зависит от наличия ссылки в строке: `ВЫБРАТЬ ФЛ.Наименование`
без ссылки ушёл бы открытым. При включённом псевдониме различимость даёт `Код`.

Координаты: `MCP_Config.МаскиПолейТиповLLM` (признак), `MCP_Security.ПолеНужноМаскироватьПоТипуLLM`
и `ПредставлениеЗакрытоPrivacy` (оба решателя — гейт запроса и второй эшелон),
`ПолеКлассаИмениОбъектаPrivacy` (класс). Порт: кейсы F1–F8 в
`scripts/privacy_mask_marking_port.mjs` (109 PASS). Порт при разработке правки поймал
две незакрытые линии подряд — колонку `Наименование` и `ПРЕДСТАВЛЕНИЕ()` — обе были
бы обнаружены только живой приёмкой.

### 6.2. Форма

Кнопки — ровно три (уточнение заказчика 11.08: прочитать, записать, очистить): **Записать**, **Перечитать**, **Очистить всё**. Команда **Импортировать из MCP_ServerConfig** — в подменю «Ещё» (разовая, миграционная — на панели ей не место). Ссылка **Настройки** внизу — не команда-действие, а показ/скрытие нижней панели. Плюс индикатор «есть несохранённые изменения» (заголовок формы со `*` достаточно).

**Левое дерево `ДеревоМетаданных`** — колонки:

| Колонка | Тип | Смысл |
|---|---|---|
| `Пометка` | Число 0/1/2 | у объекта: 0 — тип не участвует, 1 — помечено всё (все поля + псевдоним), 2 — частично; изменение пользователем каскадит (0 — снять всё у объекта, 1 — пометить все поля и псевдоним). У вида — вычисляемый индикатор, только просмотр |
| `Синоним` (+`Имя`, `ПолноеИмя`) | Строка | представление; `ПолноеИмя` = `Справочник.Контрагенты` |
| `Псевдоним` | Булево | тип входит в `type_aliases`; доступен только объектам ссылочных видов (перечень — `ВидСоСсылкойPrivacy`, `MCP_Config.bsl:1279`: Справочник, Документ, ПланСчетов, ПВХ, ПВР, ПланОбмена, БизнесПроцесс, Задача) |
| `Префикс` | Строка (50) | редактируемая; активна при `Псевдоним=Истина`; при включении флажка, если пусто — автозаполнение `Имя + "-"` (пользователь укорачивает руками: «ДокФЛ-» автоматом не получить) |

Полный состав колонок, включая служебные (`ПомеченныеПоля`, доп-ключи записей), и пообъектная инструкция по переработке формы — Приложение А.

Виды метаданных в дереве (M-20): Справочники, Документы, ПланыОбмена, ПланыСчетов, ПланыВидовХарактеристик, ПланыВидовРасчета, БизнесПроцессы, Задачи, РегистрыСведений, РегистрыНакопления, РегистрыБухгалтерии, РегистрыРасчета. Регистрам псевдонимы недоступны (нет ссылки/uuid) — только маски полей; пример `РегистрСведений.ДокументыФизическихЛиц` с префиксом `ДокФЛ-` из постановки реализуем как есть только если действующий читатель `ПсевдонимыТиповLLM` его принимает — сверить с валидацией «псевдонимы только у ссылочных видов» (`MCP_Config.bsl:551-559`): по текущему коду такая запись отклоняется с предупреждением, значит для регистров UI предлагает только маски полей, а постановочный пример реализуется через `type_field_masks`.

**Правое дерево `РеквизитыОбъекта`** — для текущей строки левого дерева: группы полей и ТЧ → поля, `Пометка` — **Булево** (решение заказчика 11.08: пометка поля — бинарный факт, булев тип оптимален). Галка у поля = поле в `type_field_masks` данного типа. Галка у группы = помечены **все** поля группы; состояния «частично» у групп правой панели нет — частичность типа показывает левое дерево (квадратик у объекта). Клик по группе ставит/снимает все её поля.

- Формат имени поля ТЧ в `fields` **обязан соответствовать действующему читателю** `МаскиПолейТиповLLM` (`MCP_Config.bsl:692-840`) и движку пометки: сверить и зафиксировать в тестах, не изобретать свой (M-21). Если читатель понимает только плоские имена — писать плоское имя поля ТЧ и предупреждать на форме о коллизии одноимённого поля шапки.

**Панель «Настройки»** (внизу, раскрывается ссылкой):

- `masked_fields` — редактируемый список имён полей («маскируются у всех объектов сразу»);
- `publish_details` — флажок;
- таблица **«Записи вне этой конфигурации»** — записи политики, чей `type` не найден в метаданных текущей базы (§6.4);
- поле предпросмотра итогового JSON (только чтение) — для сверки и приёмки; отдельной кнопки нет, обновляется автоматически при раскрытии панели и после «Записать».

### 6.3. Производительность и хранение пометок (ERP — обязательный ориентир)

Жадное построение правых деревьев для всех объектов, как в заготовке, недопустимо: на ERP это тысячи объектов и сотни тысяч полей в реквизите формы. Требование (M-22) — состояние живёт в левом дереве, правая панель лишь отображает:

- у строки объекта левого дерева есть служебная колонка `ПомеченныеПоля` (имена помеченных полей строкой); при чтении политики она заполняется из `type_field_masks` сразу для всех типов — пометки не теряются, даже если строку ни разу не открывали;
- правая панель — один реквизит формы `ПоляОбъекта`, перестраивается лениво при активизации строки объекта (метаданные + `ПомеченныеПоля`); изменение галки поля немедленно синхронизирует `ПомеченныеПоля` текущей строки;
- при «Записать» `type_field_masks` собирается напрямую из левого дерева (`ПомеченныеПоля` + служебные колонки доп-ключей), без обхода правых панелей.

Детальная схема колонок и обработчиков — Приложение А.

### 6.4. Чтение (ПриСозданииНаСервере и «Перечитать»)

Прочитать `Значение` элемента `НастройкиМаскирования` → разобрать JSON → расставить: `Псевдоним`/`Префикс` из `type_aliases`, пометки полей из `type_field_masks`, панель из `masked_fields`/`publish_details`. Сопоставление имён типов и полей — нормализованное, как у серверных читателей (регистр, `_`, `-`, `ё`).

- Записи с типами, не найденными в метаданных базы, НЕ выбрасываются: показываются в таблице «Записи вне этой конфигурации» и сохраняются при записи как есть (M-23). Политика переносима между конфигурациями; обработка, молча теряющая запись, — источник тихой утечки на другом контуре.
- Неизвестные ключи `privacy` складываются в реквизит формы и сохраняются при записи (round-trip, M-14).
- Битый JSON при чтении: форма открывается пустой с явным предупреждением «политика нечитаема, на сервере действует аварийный режим; „Записать“ перезапишет содержимое» — и показывает сырой текст в предпросмотре.
- «Перечитать» при несохранённых изменениях — вопрос пользователю.

### 6.5. Запись («Записать»)

Собрать `privacy`: `masked_fields` (панель) + `type_aliases` (строки с `Псевдоним=Истина`; пустой префикс — ошибка валидации формы, запись не выполняется) + `type_field_masks` (по §6.3, с сохранением дополнительных ключей записей M-14) + `publish_details` + записи вне конфигурации + прочие ключи. Сериализация — `ЗаписьJSON` с отступами (человекочитаемо, диффится в истории). Запись в предопределённый элемент через объект справочника.

После записи — сразу показать результат применения: вызвать `MCP_Config.ИнформацияМаскированияLLM()` и вывести на форму `enabled`, количество применённых записей, `config_warnings`, `config_errors` (M-24). Пользователь немедленно видит, как сервер понял его политику, — это замена ручной пробы после каждой правки константы.

### 6.6. «Очистить всё» и «Импортировать из MCP_ServerConfig»

- **Очистить всё**: с подтверждением снять все пометки, псевдонимы, префиксы, `masked_fields`, записи вне конфигурации (непостроенные ленивые деревья считаются пустыми — очистка обнуляет и их вклад). В справочник не пишет; фиксация — кнопкой «Записать».
- **Импортировать из MCP_ServerConfig**: миграция §7.1 — заполняет форму снимком действующей политики константы. В справочник не пишет; фиксация — кнопкой «Записать». Секции `privacy` в константе нет → сообщение «в MCP_ServerConfig нет секции privacy, импортировать нечего». Форма не пуста → предупредить, что импорт заменит содержимое.

Кнопки «Настройки по умолчанию» нет — обоснование в §3.1.

## 7. Миграция контуров

### 7.1. Механизм

Команда «Импортировать из MCP_ServerConfig» в обработке. Читает секцию `privacy` константы и строит канонический JSON §4:

- `masked_fields`, `type_aliases`, `type_field_masks`, `publish_details` — переносятся как есть;
- `organization_aliases.enabled=true` → записи `type_aliases`: `Справочник.Организации` с настроенным `prefix` (дефолт `Орг-`) — по факту наличия типа в конфигурации;
- `person_aliases.enabled=true` → записи `type_aliases` для `Справочник.ФизическиеЛица` (`physical_person_prefix`, дефолт `ФЛ-`), `Справочник.Сотрудники` (`employee_prefix`, дефолт `Сотр-`), `Справочник.Пользователи` (`user_prefix`, дефолт `Польз-`) — по факту наличия типов;
- **материализация R-12**: для каждого типа персон найти все подчинённые ему справочники (владелец — тип персоны) и добавить их в `type_aliases` с префиксом физлиц; автозакрытия в коде больше нет, невыписанная запись = утечка (сегодняшнее правило — `ЭтоПодчиненныйТипуПерсонPrivacy`, `MCP_Security.bsl:1695`);
- **материализация чувствительных полей персон**: зашитый список (`MCP_Config.bsl:412-421`: Фамилия, Имя, Отчество, СерияПаспорта, НомерПаспорта, ИндивидуальныйНомер, СтраховойНомер, ДатаРождения) → записи `type_field_masks` для каждого типа персон и подчинённых, у которых такие поля есть.

Результат показывается в форме (включая предпросмотр JSON) и фиксируется кнопкой «Записать» — в единственный элемент `НастройкиМаскирования`. Импорт сам в справочник не пишет: администратор обязан увидеть, что именно переносится, до того как это станет действующей политикой. Константу рубильника ставит в `Истина` та же процедура записи, если политика непуста и константа ещё не задана.

### 7.2. Порядок деплоя и правила проекта

1. Объекты метаданных + код — одной сборкой (новая сборка без справочника при включённом рубильнике уводит контур в аварийный режим — это правильно, но живой контур в таком состоянии не оставлять).
2. Миграция политики через команду обработки; сверка предпросмотром JSON.
3. Проверка эквивалентности (§9) на канарейке **ERP_DEMO** первой (правило канарейки волны 2). ERP-специфика: `person_aliases` там выключены и физлица политикой не покрыты (B-3 реестра) — миграция **не добавляет** покрытие втихую, фиксирует как есть; B-3 остаётся вопросом состава политики, теперь решаемым галками без деплоя.
4. Удаление секции `privacy` из `MCP_ServerConfig` (до удаления работает предупреждение M-12).
5. **Парный маркер деплоя** (правило CLAUDE.md): `engine_revision` И поведение — `get_current_user_context` отвечает, в privacy-блоке НЕТ ключей `organization_aliases`/`person_aliases`, `list_metadata_objects` возвращает имена типов. Обе прошлые аварии волны 2 ловились именно парной проверкой.

Живьём (третья сессия, после деплоя, канарейка ERP первой):

5. Парный маркер (§7.2 п.5) на всех трёх контурах.
6. Матрица волн 1–2 пофамильно (та же, что приёмка 10–11.08): эквивалентность масок до/после переезда на BUH/ZUP/ERP; различимость кодов P-0c — повторить замер 8 типов.

8. Аварийный режим: битый JSON в элементе → максимальная маска, `config_errors` непусто, сервис жив; пустой элемент → `enabled=false` без аварии.
9. Обработка на ERP: открытие формы приемлемо по времени (ленивое построение — M-22), пометки политики видны, пометки в обеих таблицах отображаются флажками, а не числами (А.5), запись из формы меняет ответы сервера без публикации.

## 10. Риски

- **R-12 больше не сам**: новый подчинённый справочник персон не закроется автоматически. Стражи: предупреждение HR-06 от `type_aliases` (M-13) + регламент «после обновления конфигурации открыть обработку и просмотреть предупреждения».
- **Рассинхрон код/справочник при частичном деплое** — закрывается аварийным режимом и парным маркером.
- **Права**: чтение политики только в привилегированном режиме (M-3), иначе ограничение прав сервисного пользователя на справочник обернётся аварийным режимом на ровном месте.
- **Производительность чтения политики**: справочник читается по требованию, как константа сейчас; если живой замер покажет деградацию — кэширование выносится в отдельную задачу (в этом ТЗ не делается).
- **Формат полей ТЧ** в `fields` — единственное место, где обработка может разойтись с движком; закрыто требованием сверки M-21 и круговым тестом.

│  │        (Псевдоним и Префикс: Доступность = НЕ ЭтоВид И вид ссылочный; служебные колонки не выводятся)
│  └─ ГруппаПоля

Заголовки «Объекты метаданных:» и «Поля и табличные части:» — как на скриншоте заказчика, остаются. Картинки строк (`ИндексКартинки`, `СоответствиеРеквизитовИНомерКартинки` `:1037`) — сохранить, если коллекция картинок доступна; иначе допустимо убрать вместе с колонкой.

**Отображение колонок пометок** (редакция 1.5.0, решение заказчика 11.08 «булев тип оптимален»):

- **левое дерево** `ДеревоМетаданныхПометка` — данные Число 0/1/2 (агрегат участия: у объекта «частично» — основное рабочее состояние, у вида — индикатор), элемент — вид «Поле флажка»: платформа рисует трёхсостоянный флажок (пусто/галочка/квадратик). Поле ввода с числами здесь — дефект сборки (инструкция §4.5.1);
- **правая таблица** `ПоляОбъектаПометка` — данные **Булево**, флажок получается автоматически, настраивать вид не нужно. Каскад правой панели булев и живёт в модуле формы (группа → все поля; поле → пересчёт группы И-агрегатом); `ИзменениеПометки` модуля объекта правой панелью больше не используется.

### А.8. Новые серверные процедуры (контракты)

Модуль формы (сервер):

- `ПрочитатьПолитикуВФорму(ТекстJSON)` — разбор §6.4: заполняет `Псевдоним`/`Префикс`/`ПомеченныеПоля`/доп-ключи по строкам дерева, `МаскируемыеПоля`, `ПубликоватьДетали`, `ЗаписиВнеКонфигурации`, `ПрочиеКлючиPrivacyJSON`; пересчитывает пометки. Битый JSON — `ЕстьОшибка`/`ТекстОшибки`, форма пустая, сырой текст в `ПредпросмотрJSON`.
- `СобратьПолитику()` → Строка — сборка §6.5 из формы (валидация префиксов: пустой — исключение с понятным текстом; дубль префикса у разных типов — предупреждение).
- `ЗаписатьПолитикуНаСервере()` — `СобратьПолитику()` → запись в элемент `НастройкиМаскирования` (объект справочника, привилегированный режим) → `MCP_Config.ИнформацияМаскированияLLM()` → вернуть `enabled`/счётчики/`config_warnings`/`config_errors` для показа (M-24).
- `ПостроитьПоляОбъекта(ИдентификаторСтроки)` — ленивое построение правой панели (§6.3).
- `ИмпортироватьИзServerConfigНаСервере()` — миграция §7.1.

Модуль объекта обработки (переработка заготовки — А.11); итоговый состав после
редакций 1.5.0–1.6.0 — ровно две функции:

- `ВидыМетаданныхДляМаскирования()` — таблица А.9; переработка `СписокОбъектовМетаданных` (`ОМ:56`) без версионных вилок;
- `ПрефиксПоУмолчанию(ИмяОбъекта)` — новая: `ИмяОбъекта + "-"`.

Каскад пометок SDCH удалён в 1.5.0 (правая панель булева, каскад в модуле формы),
регистрация БСП с обвязкой — в 1.6.0 (обработка — объект расширения, §3.3).

### А.10. Тонкие места (проверяются приёмкой)

1. **`ПолноеИмя` в единственном числе** — брать `ОбъектМетаданных.ПолноеИмя()`, не склейку заготовки (`:114`); иначе вся записанная политика окажется с несуществующими видами `Справочники.*` и движок её молча не применит (предупреждения, нулевое покрытие).
2. **Пометка вида — только просмотр**: массовая простановка на вид (все справочники ERP) запрещена интерфейсом, а не подтверждением.
3. **Ленивость** (§6.3): при открытии формы не строится ни одна правая панель; `ПомеченныеПоля` заполняются чтением политики без обхода метаданных полей.
4. **Запись в привилегированном режиме** и только целиком (никаких построчных записей, в отличие от SDCH, где настройка писалась по объекту).
5. **Переименование M-25**: после переработки поиск `ИсторияДанных`/`ИсторииДанных`/`SDCH`/`Sidorenko` по модулям пуст — лицензионная шапка заготовки удалена вместе с последним дословным фрагментом (каскадом пометок).
